## 1. Project Overview

ACIRA (**Autonomous Cyber Incident Response Agent**) is a cybersecurity automation system built specifically to address the threat landscape of **banking and financial services**. It simulates the role of a Security Operations Center (SOC) analyst by:

- Continuously ingesting structured security event logs (JSON)
- Engineering behavioral features from raw events
- Running an **Isolation Forest** ML model to score every event for anomalousness
- Applying a **rule-based + multi-factor probabilistic correlation engine** to cluster anomalous events into meaningful _incidents_
- Scoring each incident on multiple dimensions (resource impact, time patterns, IP risk, event pattern) to produce a single **Correlation Strength** value
- Computing a **Fidelity Score** — a composite weapon that determines overall incident severity
- Calling a **local LLM (Mistral via Ollama)** to generate a fully-written, technically precise, banking-specific Incident Response Playbook for any detected incident
- Exposing all of this through a **FastAPI REST API** with a professional **SOC-style web dashboard**

## 5. Core Modules — Deep Dive

### 5.1 Data Ingestion (`core/ingestion.py`)

**Purpose:** Parse raw JSON log files or API-supplied log arrays into strongly-typed Python objects.

#### `LogEvent` class

The fundamental data unit throughout the entire pipeline. Every log entry is parsed into a `LogEvent` instance:

```python
class LogEvent:
    user_id: str            # Identity of the actor (e.g., "user_23")
    ip_address: str         # IPv4 address of the event source
    event_type: str         # Type of action (see below)
    timestamp: datetime     # ISO 8601 parsed to datetime object
    resource_accessed: str  # Target resource (e.g., "customer_financial_db")
    anomaly_score: float    # Initially None; computed by anomaly.py
```

**Supported event types:**

- `login_success` — Authenticated access
- `login_failed` — Authentication failure (brute-force signal)
- `file_access` — File system access
- `db_access` — Database query/access
- `privilege_escalation` — Account elevation event

The `timestamp` field is immediately deserialized from ISO string to a `datetime` object, enabling arithmetic operations in the correlation engine (time delta calculations, ordering, etc.).

**`to_dict()` method** — Converts back to a JSON-serializable dictionary, with `timestamp` re-serialized to ISO string format. Used when building API responses.

#### `load_logs()` function

Reads `data/sample_logs.json` by default, but accepts any file path. Sorts all events chronologically by timestamp before returning them. Any missing file triggers a `FileNotFoundError` early.

### 5.2 Synthetic Log Generator (`core/synthetic_log_generator.py`)

**Purpose:** Generate a realistic, labeled dataset that simulates both normal user activity and embedded multi-stage cyberattack patterns.

**Why it exists:** Real banking log datasets are classified and unavailable publicly. This generator creates a controlled dataset where attack patterns are known and deterministic, making it ideal for testing the full pipeline without real data.

#### Normal User Population (users 1–100)

For each of 100 normal users:

- **Internal IP** — Always `192.168.1.X` (private range, flagged as low-risk)
- **Login success** at business-hours timestamp
- **File access** to non-sensitive public resources (`public_docs`, `reports`, `training_material`, `internal_policy_docs`)
- **Optional DB access** (40% probability) to non-sensitive databases (`employee_db`, `sales_db`, `analytics_db`)

This generates approximately 240 normal log entries as baseline.

#### Attack Simulation (Suspicious Users: `user_23`, `user_47`, `user_88`)

Each suspicious user follows the **complete Account Compromise Attack Chain**:

```
Step 1: 3× login_failed  (brute-force phase)
         → from external IP (not 192.168.x.x range)
         → at unusual hours: 1AM–4AM (odd_hour_flag = 1)

Step 2: login_success     (credential compromise achieved)
         → same external IP

Step 3: db_access         (lateral movement + data exfiltration)
         → resource: "customer_financial_db" (highest sensitivity)

Step 4: privilege_escalation  (persistence / account takeover)
         → resource: "core_banking_admin_panel" (critical asset)
```

This 4-part attack chain is precisely the pattern the correlation engine is designed to detect. All events are then sorted chronologically and written to `data/sample_logs.json`.

### 5.3 Feature Engineering (`core/feature_engineering.py`)

**Purpose:** Transform raw `LogEvent` objects into a structured numerical `pd.DataFrame` that can be fed into a scikit-learn/PyOD ML model.

#### Why Feature Engineering is Necessary

Machine learning models cannot understand strings like `"login_failed"` or `"192.168.1.45"`. Feature engineering translates human-readable security semantics into numerical signals that the Isolation Forest can learn from.

#### Features Extracted (6 per event)

| Feature                     | Type         | Logic                                                                            |
| --------------------------- | ------------ | -------------------------------------------------------------------------------- |
| `login_hour`                | int (0–23)   | Raw hour of the event timestamp                                                  |
| `odd_hour_flag`             | binary (0/1) | 1 if hour < 6 AM or > 10 PM (off-hours activity)                                 |
| `failed_login_count`        | int          | Pre-computed: total `login_failed` count for this user across the entire log set |
| `sensitive_access_flag`     | binary (0/1) | 1 if `"customer"` appears in `resource_accessed`                                 |
| `privilege_escalation_flag` | binary (0/1) | 1 if `event_type == "privilege_escalation"`                                      |
| `suspicious_ip_flag`        | binary (0/1) | 1 if IP does NOT start with `"192."` (external IP)                               |

**Pre-computation of `failed_login_count`:** A user-level aggregation pass runs before the per-event loop. This ensures that when scoring any individual event for a user, the total brute-force pressure from that user's entire session history is captured — not just per-event state.

The resulting DataFrame has shape `(N_events, 6)` and is passed directly to the anomaly detection module.

---

### 5.4 Anomaly Detection (`core/anomaly.py`)

**Purpose:** Train an unsupervised ML model on the feature matrix and compute a normalized anomaly score for every event.

#### Model: Isolation Forest (via PyOD)

**Isolation Forest** is the state-of-the-art algorithm for unsupervised anomaly detection. It works by:

1. Randomly selecting a feature and a split value
2. Recursively partitioning data until each point is isolated
3. Anomalous points (rare, different) are isolated in fewer splits → shorter path length → higher anomaly score

**Configuration:**

```python
IForest(contamination=0.2, random_state=42)
```

- `contamination=0.2` — Assumes 20% of events may be anomalous (generous estimate for security contexts)
- `random_state=42` — Reproducible results

#### Scoring Process

1. `model.fit(feature_df)` — Trains the model on all events in this batch
2. `model.decision_function(feature_df)` — Returns raw scores (not normalized, can be negative)
3. **Min-Max Normalization:**
   ```python
   normalized = (score - min_score) / (max_score - min_score + 1e-8)
   ```
   The `1e-8` prevents division by zero when all scores are identical.
4. Each `LogEvent.anomaly_score` is set as a `float` rounded to 4 decimal places in range `[0.0, 1.0]`

**Score Interpretation:**

- Scores near `1.0` → Highly anomalous events (attack patterns)
- Scores near `0.0` → Normal baseline behavior
- The contamination threshold means ~20% of events will be labeled as anomalous by the model's internal binary classifier, but all events receive a continuous score

### 5.5 Correlation Engine (`core/correlation.py`)

**Purpose:** Group individual anomalous events into coherent **incidents** using attack-pattern rules, then compute a multi-factor **Correlation Strength** score that reflects the true threat level of each incident.

This is the most sophisticated module in the entire system.

#### Phase 1: Incident Detection (`detect_incidents()`)

**Algorithm:**

```
1. Group all events by user_id → dict[user_id → sorted event list]
2. Per user, scan for the attack chain sequence (stateful FSM):
   - Count login_failed events (must reach ≥ 3)
   - Detect login_success AFTER 3+ failures
   - Detect db_access after login_success
   - Detect privilege_escalation → INCIDENT TRIGGERED
3. Creates Incident object, resets state, assigns sequential incident_id
```

**Finite State Machine (Attack Pattern:**

```
[login_failed × 3+]  →  [login_success]  →  [db_access]  →  [privilege_escalation]
                                                                     ↓
                                                            Incident created
```

Only complete chains produce incidents. Partial chains (e.g., failed logins with no escalation) are not flagged.

#### Phase 2: Metric Calculation (`Incident.calculate_metrics()`)

After an incident is created, `calculate_metrics()` computes two key scores:

##### 2a. Average Anomaly Score

```python
avg_anomaly_score = mean(event.anomaly_score for all events in incident)
```

Simple arithmetic mean of the ML model's per-event scores.

##### 2b. Correlation Strength — Multi-Factor Engine

The Correlation Strength is computed from **5 distinct sub-scores**, each capturing a different dimension of threat:

**Factor 1: Time Score (Burstiness / Attack Velocity)**

```python
timestamps = [e.timestamp.timestamp() for e in events]
intervals = [t2 - t1 for t1, t2 in zip(timestamps, timestamps[1:])]
total_duration = timestamps[-1] - timestamps[0]
time_score = math.exp(-total_duration / 3600)  # Exponential decay over 1 hour
```

- If an attack happens in **minutes** → `time_score` near 1.0 (highly suspicious, automated)
- If spread over **hours** → `time_score` decays toward 0 (could be coincidental)
- Uses exponential decay: `e^(-t/3600)` where t is total attack duration in seconds

**Factor 2: Resource Criticality Score**

```python
critical_weights = {
    "core_banking_admin_panel": 1.0,    # Maximum criticality
    "swift_gateway":            1.0,    # Maximum criticality
    "customer_financial_db":    0.9,    # Near-maximum
    "payroll_db":               0.8,
    "employee_db":              0.7,
    "analytics_db":             0.6,
    "NA":                       0.1     # Minimum (no resource)
}
resource_score = mean(critical_weights.get(e.resource_accessed, 0.3) for e in events)
```

Unknown resources default to 0.3 (moderate risk). This is domain knowledge embedded directly into the engine.

**Factor 3: IP Risk Profiling (Simulated Threat Intelligence)**

```python
for ip in unique_ips:
    ip_hash = int(hashlib.md5(ip.encode()).hexdigest(), 16) % 100
    if ip.startswith("192.168."):
        score += 0.2   # Low risk — internal IP
    elif ip_hash > 80:
        score += 0.95  # High risk — simulated malicious IP
    else:
        score += 0.5   # Unknown external
```

- Internal IPs (`192.168.x.x`) are low-risk by default
- External IPs are "checked" against a simulated threat intelligence feed using MD5 hashing to produce deterministic but varied risk scores
- IP Consistency penalty: multiple different IPs used = lower `ip_consistency = 1.0 / len(unique_ips)`
- Final IP score: `(avg_risk * 0.7) + (ip_consistency * 0.3)`

**Factor 4: Pattern Cohesion Bonus**

```python
has_priv_esc    = any(e.event_type == "privilege_escalation" for e in events)
has_failed_logins = any(e.event_type == "login_failed"         for e in events)
pattern_bonus = 0.2 if (has_priv_esc and has_failed_logins) else 0.0
```

A manual `+0.2` bonus is applied when the classic credential-compromise-to-escalation pattern is confirmed in the same incident.

**Factor 5: Weighted Ensemble + Sigmoid Squash**

```python
base_score = (resource_score * 0.4) + (time_score * 0.3) + (final_ip_score * 0.2) + pattern_bonus

# Damping to prevent identical scores
damping = (incident_id % 10) * 0.001

# Sigmoid squash to 0.05–0.95 range
final_score = 0.95 / (1 + math.exp(-5 * (base_score - 0.5))) + damping
correlation_strength = min(max(final_score, 0.05), 0.99)
```

**Ensemble Weights:**
| Factor | Weight | Rationale |
|---|---|---|
| Resource Criticality | 40% | The target asset determines maximum damage potential |
| Time/Burstiness | 30% | Fast attacks are automated → higher threat |
| IP Risk | 20% | Source reputation affects confidence |
| Pattern Bonus | 10% | Structural confirmation of known attack pattern |

**Sigmoid Squash:** Centers the score at 0.5 and squashes the output into a [0.05, 0.99] range, preventing extreme values while maintaining sensitivity to differences between incidents.

### 5.6 Fidelity Scoring (`core/scoring.py`)

**Purpose:** Combine the ML anomaly score, the correlation engine score, and rule-based certainty into a single **Fidelity Score** that represents the analyst's confidence that this is a real, critical incident.

#### Formula

```python
fidelity = (0.5 × avg_anomaly_score) + (0.3 × correlation_strength) + (0.2 × rule_severity)
```

| Component              | Weight  | Source                                             |
| ---------------------- | ------- | -------------------------------------------------- |
| `avg_anomaly_score`    | **50%** | ML model output (how unusual are the events?)      |
| `correlation_strength` | **30%** | Correlation engine (how dangerous is the pattern?) |
| `rule_severity`        | **20%** | Hard-coded `1.0` for confirmed attack chains       |

`rule_severity` is fixed at `1.0` for the known 4-stage attack pattern (brute-force → escalation). In a production system, this would come from a rule library with varying severities per pattern type.

#### Severity Classification

| Fidelity Score | Severity Label  |
| -------------- | --------------- |
| > 0.75         | 🔴 **Critical** |
| > 0.50         | 🟠 **High**     |
| ≤ 0.50         | 🟡 **Medium**   |

### 5.7 Playbook Generator (`core/playbook.py`)

**Purpose:** Automatically generate a detailed, banking-specific Incident Response Playbook for any detected incident by sending a structured prompt to a locally-running Mistral LLM via Ollama.

#### How It Works

1. **Builds Incident Summary JSON:**

```json
{
  "incident_id": 1,
  "user_id": "user_23",
  "ip_address": "73.142.55.201",
  "avg_anomaly_score": 0.9123,
  "correlation_strength": 0.8741,
  "fidelity_score": 0.8872,
  "severity": "Critical",
  "event_types": [
    "login_failed",
    "login_failed",
    "login_failed",
    "login_success",
    "db_access",
    "privilege_escalation"
  ]
}
```

2. **Constructs a SOC Analyst System Prompt:**
   - Establishes the LLM's persona as a "senior banking SOC analyst"
   - Includes strict output format rules (4 sections: Containment, Eradication, Recovery, Reporting)
   - Provides conditional logic instructions (e.g., if `privilege_escalation` + `db_access` → confirmed account compromise)
   - References specific user IDs and IPs in the prompt to force personalized, non-generic responses
   - Explicitly restricts hallucination patterns (no malware mentions unless indicated, no filler text)

3. **Calls Ollama via subprocess:**

```python
result = subprocess.run(
    ["ollama", "run", "mistral"],
    input=prompt,
    capture_output=True,
    text=True,
    encoding="utf-8",
    errors="ignore"
)
return result.stdout.strip()
```

The LLM runs **locally** — no cloud API calls, no data leaves the machine. Mistral is a 7B parameter model that runs efficiently on consumer hardware.

#### Output Format

```
=== INCIDENT RESPONSE PLAN ===

Severity: Critical

1. Containment:
   - Immediately suspend user_23's account
   - Block external IP 73.142.55.201 at firewall level
   - Revoke all active sessions for user_23

2. Eradication:
   - Audit customer_financial_db access logs for data exfiltration
   - Review privilege changes made via core_banking_admin_panel
   - Reset all credentials shared with user_23

3. Recovery:
   - Restore account access after forensic confirmation
   - Enforce MFA re-enrollment for all privileged users
   - Validate database integrity via checksums

4. Reporting:
   - Submit incident report to CISO within 2 hours
   - Log event in SIEM with incident_id: 1
   - Notify compliance team per banking regulatory requirements
```

## 6. API Layer — Deep Dive (`api/main.py`)

**Framework:** [FastAPI](https://fastapi.tiangolo.com/) — async-capable, auto-documented, Pydantic-validated.

**Base URL:** `http://127.0.0.1:8000`

**Auto Docs:** `http://127.0.0.1:8000/docs` (Swagger UI available automatically)

### CORS Configuration

```python
app.add_middleware(
    CORSMiddleware,
    allow_origins=["*"],
    allow_credentials=True,
    allow_methods=["*"],
    allow_headers=["*"],
)
```

All origins allowed for demo purposes. Restricts in production to specific dashboard origin.

### In-Memory Cache

```python
cached_incidents = []
```

A module-level global list holds the most recently analyzed incidents. This allows the `/incidents` GET endpoint to return results without re-analyzing. It is overwritten on every `POST /analyze` call.

### Input Validation — `LogInput` Pydantic Model

```python
class LogInput(BaseModel):
    user_id: str
    ip_address: str
    event_type: str
    timestamp: str
    resource_accessed: str
```

FastAPI automatically validates incoming JSON against this schema. Invalid fields produce a `422 Unprocessable Entity` response with detailed error messages.

### Endpoint 1: `POST /analyze`

**Accepts:** Optional list of `LogInput` objects (JSON array)

**Logic:**

1. If `log_data` is provided → Convert to `LogEvent` objects, sort by timestamp
2. If no data provided → Fall back to `load_logs()` from `data/sample_logs.json`
3. Run the complete pipeline: `extract_features` → `compute_anomaly_scores` → `detect_incidents`
4. For each incident: `compute_fidelity_score()` → enrich with `fidelity_score` + `severity`
5. Store enriched incidents in `cached_incidents`
6. Return: `{ "total_incidents": N, "incidents": [...] }`

### Endpoint 2: `GET /incidents`

**Returns:** Current `cached_incidents` list (whatever the last analysis produced)

**Use case:** Dashboard loads on page open and fetches any previously cached results without re-triggering an expensive re-analysis.

### Endpoint 3: `GET /playbook/{incident_id}`

**Logic:**

1. Find the incident with matching `incident_id` in `cached_incidents`
2. Reconstruct `LogEvent` objects from the stored dict representation
3. Reconstruct a lightweight `Incident` object with pre-computed scores
4. Call `generate_playbook(incident)` → Ollama LLM call
5. Return: `{ "incident_id": N, "playbook": "..." }`

**Why reconstruction?** Incidents are stored as plain dicts (JSON-serializable) in the cache. The playbook generator needs `Incident` objects. Rather than storing Python objects in memory (which would break JSON serialization), the API reconstructs them on-demand from the dict representation.

## 9. End-to-End Request Lifecycle

Here is what happens when you upload a log file in the dashboard and click "Analyze Uploaded Logs":

```
1. [Browser] User selects sample_logs.json and clicks "Analyze"
   ↓
2. [JavaScript] FileReader reads file bytes → JSON.parse() → Array of log objects
   ↓
3. [HTTP] POST /analyze with Content-Type: application/json
          Body: [{user_id, ip_address, event_type, timestamp, resource_accessed}, ...]
   ↓
4. [FastAPI] Pydantic validates every list item against LogInput schema
   ↓
5. [api/main.py] Creates LogEvent objects, sorts by timestamp
   ↓
6. [feature_engineering.py] For each event, computes 6 binary/numerical features
   Returns: pd.DataFrame(shape=(N, 6))
   ↓
7. [anomaly.py] IForest.fit(df) — trains on all events in this batch
   IForest.decision_function(df) → raw scores array
   Min-max normalize → sets event.anomaly_score on each LogEvent
   ↓
8. [correlation.py] Groups events by user_id
   Scans for: 3 login_failed → login_success → db_access → privilege_escalation
   Matches found for user_23, user_47, user_88
   Creates 3 Incident objects, calls calculate_metrics() on each
   Computes correlation_strength (multi-factor: 0.05–0.99)
   ↓
9. [scoring.py] For each incident:
   fidelity = 0.5 * avg_anomaly_score + 0.3 * correlation_strength + 0.2 * 1.0
   Assigns severity: Critical / High / Medium
   ↓
10. [api/main.py] Builds enriched_incidents list
    Stores in cached_incidents global
    Returns JSON: {total_incidents: 3, incidents: [...]}
    ↓
11. [Browser] renderIncidents() populates table with 3 rows
    Status banner: "Analysis Complete! 3 incidents detected." (red)
    ↓
12. [User] Clicks "Generate Plan" on Incident #1
    ↓
13. [HTTP] GET /playbook/1
    ↓
14. [api/main.py] Finds incident_id=1 in cached_incidents
    Reconstructs LogEvent + Incident objects from dict
    Calls generate_playbook(incident)
    ↓
15. [playbook.py] Builds structured banking SOC prompt
    subprocess.run(["ollama", "run", "mistral"]) — local LLM call
    Returns multi-section incident response plan (stdout)
    ↓
16. [Browser] playbookContainer.innerText = data.playbook
    Full playbook displayed in monospace panel
```

## 10. How Each Component Connects

```
ingestion.py
    ↓ supplies List[LogEvent]

feature_engineering.py
    ↓ consumes List[LogEvent], produces pd.DataFrame

anomaly.py
    ↓ consumes pd.DataFrame, mutates LogEvent.anomaly_score

correlation.py
    ↓ consumes List[LogEvent with scores], produces List[Incident]
    ↓ calls scoring.py internally (to get fidelity for correlation calc context)

scoring.py
    ↓ consumes Incident, produces (fidelity: float, severity: str)

playbook.py
    ↓ consumes Incident, calls scoring.py, produces str (playbook text)

api/main.py
    ↓ orchestrates all of the above, exposes 3 HTTP endpoints
    ↓ maintains cached_incidents[] in memory

dashboard.html
    ↓ HTTP client consuming api/main.py endpoints
    ↓ displays results, triggers playbook generation
```

## 15. Design Decisions & Algorithms Explained

### Why Isolation Forest?

Isolation Forest is chosen over supervised methods (SVM, Random Forest classifiers) because:

- **No labeled data required** — In real security environments, you cannot label every log entry as "attack" or "normal"
- **Efficient on high-dimensional data** — Works well with the 6-feature space
- **Interpretability** — Score directly reflects isolation depth; shorter path = more anomalous
- **Configurable contamination** — Easy to adjust sensitivity without retraining from scratch

### Why Rule-Based Correlation (not purely ML)?

Attack chain detection uses explicit FSM rules rather than clustering algorithms (like DBSCAN) because:

- **Interpretability** — SOC analysts need to explain detections; rules are auditable
- **Determinism** — Same attack always produces an incident; ML clustering can be stochastic
- **Domain knowledge** — The 4-stage attack chain is a known banking threat pattern
- **Speed** — O(N) per user vs. O(N²) for similarity-based clustering

### Why Multi-Factor Correlation Strength (not just anomaly score)?

Using only the ML anomaly score would miss important context:

- A `privilege_escalation` on a non-critical asset at business hours might score anomalous by ML but is lower real-world risk
- The **resource criticality** component ensures `core_banking_admin_panel` access always scores higher than `reports` access
- The **time burstiness** component identifies automated attacks (fast, uniform timing) vs. coincidental events

### Why Sigmoid Squash?

Linear normalization of the base score would compress all incidents toward similar values. The sigmoid function `0.95 / (1 + e^(-5*(x-0.5)))`:

- Centers at 0.5 (base_score = 0.5 → correlation_strength ≈ 0.475)
- Creates a "differentiation zone" between 0.3 and 0.7 where small score differences produce visible output differences
- Naturally saturates at extremes, preventing impossible scores

### Why Local LLM (Ollama) not OpenAI/Claude?

- **Privacy** — Banking incident data cannot leave the institution's network
- **Cost** — No per-token API charges for high-volume SOC operations
- **Latency** — No network round-trip for time-sensitive incident response
- **Compliance** — Full data sovereignty; no third-party data processing agreements needed
